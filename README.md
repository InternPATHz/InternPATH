## 1. หลักการและเหตุผล (Rationale)

ในปัจจุบัน นักศึกษามหาวิทยาลัยจำนวนมากต้องเผชิญกับความเสี่ยงในการหาสถานที่ฝึกงานผ่านช่องทางออนไลน์ทั่วไป เช่น ประกาศงานที่ไม่มีการคัดกรอง งานหลอกลวงเรียกเก็บค่ามัดจำ หรือรายละเอียดงานไม่ตรงปก (Job Scam & Misrepresentation) ในขณะที่การประสานงานระหว่างนักศึกษา อาจารย์ที่ปรึกษา และสถานประกอบการมักกระจัดกระจายและขาดระบบติดตามสถานะที่เป็นมาตรฐานเดียวกัน

เพื่อแก้ปัญหานี้ คณะผู้จัดทำจึงพัฒนา **University Internship Platform (InternPath)** ในฐานะ **แพลตฟอร์มตัวกลาง (University–Industry Internship Hub)** ด้วยสถาปัตยกรรม **Microservices** ที่เชื่อมโยงระหว่าง **นักศึกษา อาจารย์จากมหาวิทยาลัย และบริษัท** เข้าด้วยกัน โดยให้ **อาจารย์เป็นผู้นำนักศึกษาในความดูแลเข้าสู่ระบบ** และมี **Platform Admin** คอยตรวจสอบและอนุมัติบัญชีบริษัทที่สมัครเข้ามา ควบคู่ไปกับระบบ **Tag ทักษะ** ที่บอกความต้องการของแต่ละตำแหน่ง ระบบรายงานประกาศงานและรีวิวที่น่าสงสัย (**Report & Auto-Suspend**) ระบบกำหนดเวลาตอบกลับและแจ้งเตือน (**SLA & Notification**) เพื่อไม่ให้กระบวนการค้าง ระบบบันทึกประวัติการเปลี่ยนสถานะที่ตรวจสอบย้อนหลังได้ (**Audit Trail**) และระบบการออกใบรับรองการฝึกงานแบบดิจิทัล (**E-Certificate**) ที่มี QR Code ให้บุคคลภายนอกตรวจสอบความถูกต้องได้ด้วยตนเอง

## 2. วัตถุประสงค์ของโครงงาน (Objectives)

1. **เพื่อออกแบบและพัฒนาแพลตฟอร์มตัวกลางเชื่อมโยงการฝึกงาน (Internship Hub) ด้วยสถาปัตยกรรม Microservices** ที่แยกส่วนการทำงานชัดเจน (แต่ละ Service มีฐานข้อมูลของตนเอง) รองรับการประมวลผลแบบ Asynchronous ผ่าน Message Broker โดยไม่กระทบต่อประสิทธิภาพหน้าเว็บหลัก
2. **เพื่อสร้างระบบควบคุมความน่าเชื่อถือของบริษัทและประกาศงาน** ผ่านการอนุมัติบัญชีองค์กรโดย Platform Admin ควบคู่กับระบบรายงานประกาศงานและรีวิว ธงตรวจสอบบริษัท และ Audit Log พร้อมกลไกป้องกันการรายงานเท็จ
3. **เพื่อพัฒนากระบวนการอนุมัติและติดตามผลฝึกงานแบบครบวงจร (End-to-End Internship Lifecycle)** เชื่อมโยงตั้งแต่ HR ตอบรับใบสมัคร → นักศึกษายืนยันข้อเสนอ → อาจารย์อนุมัติการออกฝึกงาน → บริษัทประเมินผลและออก **E-Certificate (PDF + QR ตรวจสอบได้)** → จนถึงระบบรีวิวบริษัทจากผู้ฝึกงานจริง (Closed-Loop Review)
4. **เพื่อออกแบบกระบวนการให้ครอบคลุมเส้นทางที่ไม่ปกติ** เช่น การถอนใบสมัครและการถอนข้อเสนอ การไม่ตอบสนองของแต่ละฝ่าย (SLA/Timeout) การยุติการฝึกกลางคัน การโต้แย้งผลประเมิน การรายงานปัญหาระหว่างฝึกงาน และการที่บริษัทถูกระงับระหว่างฝึก เพื่อไม่ให้ใบสมัครหรือโควตาตำแหน่งค้างอยู่ในระบบ
5. **เพื่อให้ระบบมีความปลอดภัยและตรวจสอบย้อนหลังได้** ด้วยการยืนยันตัวตนผ่านอีเมล การควบคุมสิทธิ์ตาม Role การบันทึกประวัติการเปลี่ยนสถานะและการกระทำของ Admin (Audit Log) และการคุ้มครองข้อมูลส่วนบุคคล (PDPA)

## 3. โมเดลธุรกิจและการสร้างรายได้ (Business Model)
- **Featured / Boosted Job Post:** บริการดันการ์ดประกาศงานขึ้นแสดงผลลำดับบนสุดของหน้าค้นหา พร้อมป้ายกำกับพิเศษ (`Urgent / Featured`) สำหรับบริษัทที่ต้องการรับนักศึกษาฝึกงานเร่งด่วน (ใช้ได้เฉพาะประกาศที่เป็น `PUBLISHED` แล้ว)
- **Fast-Track Account Review:** บริการตรวจเคสของบริษัทที่ติดคิว Admin แบบเร่งด่วนพิเศษ (Priority Queue, SLA 12 ชั่วโมง เทียบกับ 48 ชั่วโมงของคิวปกติ) **Fast-Track เปลี่ยนเฉพาะลำดับในคิว ไม่ลดเกณฑ์การตรวจ**
- **HR Pro Subscription (Future Phase):** แพ็กเกจสมาชิกรายเดือนสำหรับองค์กรขนาดใหญ่ เพื่อปลดล็อกโควตาการโพสต์งานไม่จำกัดและการค้นหาเรซูเม่นักศึกษาเชิงรุก (Talent Pool Search)

> **หมายเหตุสำหรับการสาธิต:** โครงงานนี้ไม่เชื่อมต่อ Payment Gateway จริง การซื้อบริการ Featured / Fast-Track จำลองโดยให้ **Platform Admin เป็นผู้เปิดสิทธิ์ให้บริษัท** แทนขั้นตอนการชำระเงิน โดยสิทธิ์ถูกเก็บเป็นฟิลด์ของบริษัท (`featured_enabled`, `fast_track_enabled`) ที่ **Identity & Organization Service** และ Service อื่นอ่านผ่าน Event `CompanyEntitlementChanged`

## 4. ขอบเขตของระบบและประเภทงาน (System Scope & Job Categories)

### 4.1 ผู้ใช้งานระบบ (Actors)
- **นักศึกษา (Student):** **ไม่ต้องสมัครสมาชิกเอง** — อาจารย์ที่ปรึกษาสร้างบัญชีให้ผ่านฟอร์มเพิ่มนักศึกษา (ระบบส่งอีเมลคำเชิญให้นักศึกษาตั้งรหัสผ่าน และผูกกับอาจารย์ผู้สร้างเป็น `LINKED` ทันที ไม่มีขั้นเลือกอาจารย์), สร้างโปรไฟล์/เรซูเม่ (ให้ความยินยอมก่อนส่งให้บริษัทแต่ละแห่ง), ค้นหาบริษัทและสมัครงาน (กรองตาม Tag ทักษะได้), **ยืนยันรับข้อเสนอจากบริษัท (ได้ทีละ 1 ที่) หรือปฏิเสธ/ถอนใบสมัคร (ถอนได้จนถึงสถานะ `ADVISOR_APPROVED`)**, ขอยุติการฝึกกลางคัน, **รายงานปัญหาระหว่างฝึกงานถึงอาจารย์และ Admin (บริษัทมองไม่เห็น)**, **โต้แย้งผลประเมิน `FAIL` ภายใน 7 วัน**, กด Report ประกาศงานหรือรีวิวที่น่าสงสัย, เขียนรีวิวบริษัทเมื่อสิ้นสุดการฝึกจริง และดาวน์โหลด **E-Certificate (PDF)** ที่บริษัทออกให้ (หลังฝึกจบด้วยผล `ACADEMIC_PASS` แล้วสมัครฝึกงานใหม่ไม่ได้ เว้นแต่ Admin ปลดล็อก)
- **ตัวแทนบริษัท / ฝ่ายบุคคล (Company / HR):** ลงทะเบียนองค์กร (ใช้อีเมลโดเมนองค์กรและยืนยันอีเมล คนแรกเป็น **Owner** เชิญ **HR Member** ได้ **กำหนดสายงาน (`Tech & IT` / `Business & Marketing` / `Corporate Services`) ให้สมาชิกแต่ละคน** และโอนสิทธิ์ Owner ได้), สร้าง/แก้ไขประกาศรับนักศึกษาฝึกงาน (กรอกข้อมูลบังคับให้ครบ เลือก Tag ทักษะ ประกาศเผยแพร่ทันที) **สมาชิกจัดการได้เฉพาะประกาศและผู้สมัครของสายงานที่ได้รับ ส่วน Owner จัดการได้ทุกสายงาน**, คัดเลือกผู้สมัครและส่งข้อเสนอ (`HR_ACCEPTED`) พร้อมระบุวันเริ่ม-สิ้นสุด, **ถอนข้อเสนอก่อนเริ่มฝึกได้พร้อมเหตุผล (`OFFER_RESCINDED`)**, **กดยืนยันว่านักศึกษาเริ่มงานจริง (ปรับวันเริ่ม-สิ้นสุดได้)**, ยุติการฝึกกลางคันพร้อมเหตุผล, **รายงานพฤติกรรมของนักศึกษาที่กำลังฝึกงานถึงอาจารย์ที่ปรึกษา** (การเข้างาน / พฤติกรรม / ผลงาน / ความปลอดภัย / อื่น ๆ — เห็นการรับทราบและหมายเหตุจากอาจารย์), ประเมินผลการฝึกงาน (`PASS` / `FAIL` โดย `FAIL` ต้องระบุเหตุผล) และกดออก/เพิกถอน **E-Certificate (PDF)** ในนามบริษัท, ตอบกลับรีวิวสาธารณะได้ 1 ครั้งต่อรีวิว
- **อาจารย์จากมหาวิทยาลัย (Advisor):** สมัครด้วย `@ac.th` พร้อมชื่อและตัวย่อมหาวิทยาลัย (ยืนยันอีเมล) และรอ Admin อนุมัติบัญชี — ได้ **รหัสอาจารย์** (ตัวย่อมหาวิทยาลัย + เลข 6 หลัก) ใช้แสดงและค้นหาแทนรหัสภายในของระบบ, **เพิ่มนักศึกษาในความดูแลด้วยฟอร์ม** (ระบบส่งอีเมลคำเชิญและผูกกับอาจารย์ทันที), ตรวจสอบและกดอนุมัติคำขอออกฝึกงาน (เช็กความตรงสายก่อนเริ่มฝึก; **การไม่อนุมัติต้องระบุเหตุผล**), ติดตามสถานะการฝึกงาน, รับแจ้ง **รายงานปัญหาระหว่างฝึกงาน** ของนักศึกษาในความดูแล, **รับรายงานพฤติกรรมจากบริษัทและกดรับทราบพร้อมหมายเหตุ**, **ตัดสินคำโต้แย้งผลประเมิน `FAIL`** (สั่งให้บริษัทประเมินซ้ำได้ 1 รอบ), ตัดสินใจเมื่อบริษัทถูกระงับขณะนักศึกษากำลังฝึก และ **บันทึกผลทางวิชาการ (`academic_result`)** ของการฝึกงานแต่ละราย
- **ผู้ดูแลแพลตฟอร์ม (Platform Admin):** ตรวจและอนุมัติบัญชีบริษัทและบัญชีอาจารย์ (`Verified by Platform`), ติดป้าย `University Partner` ให้บริษัทที่มีข้อตกลงกับมหาวิทยาลัย, **จัดการรายการ Tag ทักษะกลาง** (เพิ่ม/แก้ชื่อ/ปิดใช้งาน/รวม Tag ที่ซ้ำ/ลบ Tag ที่ยังไม่มีประกาศใช้), **จัดการรายชื่อมหาวิทยาลัย** (แก้ชื่อ ตัวย่อ และเปิด/ปิดใช้งาน), ค้นหาผู้ใช้ด้วยรหัสที่แสดง (รหัสนักศึกษา / รหัสอาจารย์ / เลขทะเบียนบริษัท), ตรวจอนุมัติประกาศงานของบริษัทที่ถูกติดธง `UNDER_REVIEW` (`Manual Review Queue`), ดูแลเคสที่ถูก Report (ประกาศงานและรีวิว), **พิจารณารายงานปัญหาระหว่างฝึกงาน**, ตรวจบัญชีบริษัทที่ถูกติดธง `UNDER_REVIEW`, เพิกถอน E-Certificate, ย้ายอาจารย์ที่ปรึกษาให้นักศึกษา, แต่งตั้ง Owner ใหม่ให้บริษัทที่ไม่มี Owner, ปลดล็อกการสมัครซ้ำ, เปิดสิทธิ์ Featured/Fast-Track (จำลองการชำระเงิน) และยืนยันเคสที่บริษัทไม่ประเมินผลนักศึกษา โดยทุกการกระทำถูกบันทึกใน Audit Log

### 4.2 ขอบเขตประเภทงานบนแพลตฟอร์ม (Supported Job Categories)
1. **สายเทคโนโลยีและดิจิทัล (Tech & IT):** เช่น Software Engineer Intern, QA/Tester, UI/UX Designer, Data Analyst
2. **สายธุรกิจ การตลาด และคอนเทนต์ (Business & Marketing):** เช่น Digital Marketing, Content Creator, Graphic Designer, Business Development
3. **สายงานสนับสนุนองค์กร (Corporate & Professional Services):** เช่น HR Intern, Administrative Intern, Corporate Finance Intern

| **1** | **Identity & Organization Service** | - **บัญชีและความปลอดภัย**: แยกสิทธิ์ 4 Roles (`STUDENT`, `COMPANY_HR`, `ADVISOR`, `PLATFORM_ADMIN`), **นักศึกษาไม่สมัครเอง: อาจารย์สร้างบัญชีนักศึกษาด้วยฟอร์ม (ส่งอีเมลคำเชิญตั้งรหัสผ่าน ผูก `advisor_id` เป็น `LINKED` อัตโนมัติ)**, ยืนยันอีเมลของอาจารย์/บริษัท, รีเซ็ตรหัสผ่าน, ออก JWT อายุสั้นพร้อม Refresh Token, Denylist สำหรับบัญชีที่ถูกระงับ, บันทึกความยินยอม PDPA และจัดการคำขอลบบัญชี<br>- **มหาวิทยาลัยและรหัสที่แสดง**: ระบุมหาวิทยาลัยจากโดเมนอีเมล เก็บชื่อและตัวย่อ (Admin แก้ได้); รหัสที่แสดงแทน UUID — นักศึกษาใช้รหัสนักศึกษา, อาจารย์ใช้รหัสอาจารย์ (ตัวย่อ + เลข 6 หลัก), บริษัทใช้เลขทะเบียน (UUID ยังเป็นรหัสภายในและใน Event)<br>- **อาจารย์**: สมัครด้วย `@ac.th` และรอ Admin อนุมัติ; เพิ่มนักศึกษาในความดูแล, ดูรายชื่อนักศึกษาพร้อมตัวกรอง (ชั้นปี / กำลังฝึกงาน / ฝึกงานเสร็จแล้ว), ย้ายอาจารย์ที่ปรึกษาโดย Admin เท่านั้น<br>- **บริษัท**: ลงทะเบียนและอนุมัติโดย Admin (`PENDING` / `NEED_MORE_INFO` / `VERIFIED` / `REJECTED` / `SUSPENDED`), ป้าย `University Partner`, HR Owner/Member **พร้อมสายงานของสมาชิก** และการโอนสิทธิ์ Owner, สิทธิ์ `featured_enabled` / `fast_track_enabled`, เอกสารยืนยันบริษัทและโลโก้<br>- **Company Directory**: หน้าสารบัญค้นหาบริษัท พร้อมคะแนนรีวิวที่รับจาก Event `ReviewPublished`<br>- หน้า Admin ของงานข้างต้น และ Audit Log ของ Service นี้<br>- ส่ง Event: `CompanyStatusChanged`, `CompanyEntitlementChanged`, `AdvisorLinkChanged`, `UserDeletionRequested` |
| **2** | **Job Management Service** | - **จัดการงานฝั่ง HR**: สร้าง/แก้ไข/ปิด การ์ดประกาศงาน (ข้อมูลบังคับและ `target_majors`) **ประกาศเผยแพร่ทันที** (เว้นแต่บริษัทถูกติดธง `UNDER_REVIEW`) สมาชิก HR จัดการได้เฉพาะสายงานที่ได้รับ<br>- **Tag ทักษะ**: เก็บรายการ Tag กลาง (Admin เพิ่ม/แก้/ปิดใช้งาน/รวม/ลบได้เมื่อไม่มีประกาศใช้), ติด Tag ให้ประกาศ 1-10 รายการ และกรองการค้นหาด้วย Tag<br>- **เป็นเจ้าของฟิลด์สถานะประกาศงานแต่เพียงผู้เดียว**: เปลี่ยนสถานะเอง (เผยแพร่ทันที) หรือตามผลที่ Verification ส่งมา แล้วส่ง `JobStatusChanged`<br>- **Job Search**: ค้นหาตำแหน่งฝึกงาน (กรองตามสายงาน, รูปแบบ, สาขา, Tag) พร้อม Snapshot ชื่อ/โลโก้/ป้ายสถานะบริษัท (อัปเดตจาก `CompanyStatusChanged`) ส่วนคะแนนดาวดึงจาก Directory ผ่าน Gateway<br>- รองรับสถานะพิเศษ `Featured Job` (อ่านสิทธิ์จาก `CompanyEntitlementChanged`)<br>- **จัดการโควตาตำแหน่งแบบ Atomic**: จอง (reserve) → ยืนยัน (confirm) → คืน (release) ตามคำสั่งจาก Lifecycle Service (ใช้ `UPDATE` แบบมีเงื่อนไขในคำสั่งเดียว)<br>- การปิดประกาศหยุดเฉพาะผู้สมัครใหม่ ใบสมัครที่ค้างอยู่ดำเนินต่อ<br>- *ไม่เก็บสถานะใบสมัคร (เจ้าของ State Machine ใบสมัครคือ Lifecycle Service)*<br>- ส่ง Event: `JobSubmitted` (เฉพาะบริษัทที่ติดธง), `JobStatusChanged` |
| **3** | **Verification & Trust Service** <br>*(Trust & Report)* | - **Admin Queue & SLA**: คิวตรวจสอบ (ประกาศของบริษัทที่ติดธง, ธงบริษัท, รายงานประกาศ, รายงานรีวิว) พร้อมป้าย `OVERDUE` เมื่อเกิน SLA และหน้า Admin ของคิวเหล่านี้<br>- **Anti-Abuse**: นับรายงานประกาศงานและส่ง `ReportThresholdReached` เมื่อครบเกณฑ์ พร้อมกลไกกันการรายงานเท็จ<br>- **เป็นเจ้าของธง `UNDER_REVIEW` ของบริษัท** (Admin ตั้ง/เคลียร์ธงผ่าน API ของ Service นี้)<br>- **Review Moderation**: รับรีวิวที่ส่งเข้ามา (`ReviewSubmitted`) แล้วส่งผลเผยแพร่ด้วย `ReviewModerationResult` ทันที (ไม่มีการสแกนคำต้องห้าม) และดูแลคิวรายงานรีวิว<br>- ไม่มี Automated Pre-Screening / Risk Score / Blacklist แล้ว (ปรับ Requirement 2026-11-21) |
| **4** | **Student Experience & Internship Lifecycle Service** | - **เจ้าของ Application State Machine ทั้งหมด**: สมัคร → HR ตอบรับ → นักศึกษายืนยัน → อาจารย์อนุมัติ → HR ยืนยันเริ่มงาน → ฝึกงาน → ประเมิน → จบ รวมถึงเส้นทางถอน/ถอนข้อเสนอ/ปฏิเสธ/หมดเวลา/ยุติกลางคัน และกฎห้ามสมัครซ้ำหลัง `ACADEMIC_PASS`<br>- **SLA Scheduler**: ตั้งเวลาเตือนและหมดอายุตามกำหนดของแต่ละขั้นตอน (เตือนครั้งเดียวต่อรายการ ใช้เขตเวลา `Asia/Bangkok`)<br>- **Pre-Internship Approval (Advisor Portal)**: คิวให้อาจารย์อนุมัติ/ไม่อนุมัติ (พร้อมเหตุผล), ตัดสินคำโต้แย้งผล `FAIL`, บันทึก `academic_result`, ติดตามนักศึกษาในความดูแล<br>- **HR Evaluation & E-Certificate**: ประเมิน (Pass/Fail), ออก **E-Certificate (PDF)** พร้อม Certificate ID + QR + หน้าตรวจสอบสาธารณะ + เพิกถอนได้ และดักเงื่อนไขฝึกจริง ≥ 30 วัน (ตั้งค่าได้ใน config)<br>- **รายงานปัญหาระหว่างฝึกงาน** (`problem_reports`) และหน้า Admin ที่เกี่ยวข้อง (ยืนยัน `NO_EVALUATION`, เพิกถอนใบรับรอง, พิจารณารายงาน)<br>- **รายงานพฤติกรรมจากบริษัท** (`conduct_reports`): HR ส่งได้เฉพาะใบสมัคร `IN_PROGRESS` ที่มีอาจารย์ที่ปรึกษา, อาจารย์ของใบสมัครนั้นกดรับทราบพร้อมหมายเหตุได้ครั้งเดียว<br>- **Fair Review System & Student Profile**: เก็บรีวิวและเผยแพร่เมื่อผ่านการตรวจจาก Verification, โปรไฟล์/เรซูเม่, Application Tracker (Timeline จาก `status_history`) และดาวน์โหลด E-Certificate<br>- ส่ง Event: `ApplicationStatusChanged`, `ReviewSubmitted`, `ReviewPublished`, `CertificateIssued` / `CertificateRevoked`, `ReminderDue`, `ConductReportCreated` |
| **5** | **Notification Service** | - รับ Event จาก Message Broker แล้วแจ้งเตือนผ่าน In-App และอีเมล (ใช้ Mailpit ใน Docker Compose สำหรับการสาธิต)<br>- Event พกเฉพาะ `user_id` แล้วดึงอีเมลปลายทางจาก Identity Service (ไม่ส่งข้อมูลส่วนบุคคลไปกับ Event)<br>- แจ้งเตือนทุกการเปลี่ยนสถานะสำคัญ, การเตือนตาม SLA, และการแจ้งอาจารย์เมื่อเกิดเคสผิดปกติ<br>- ไม่มี Business Logic ของโดเมนอื่น (ทำหน้าที่รับ Event จัดเทมเพลต และส่งข้อความเท่านั้น) |

### 4.4 เทคโนโลยีที่ใช้ (Tech Stack)

ระบบรันบนเครื่องของทีม ไม่มีการ Deploy ขึ้น Cloud: ฐานข้อมูล คิวข้อความ ที่เก็บไฟล์ และอีเมลจำลองรันใน **Docker Compose** ส่วน Service และหน้าเว็บรันด้วย **pnpm** (วิธีรันดู [docs/getting-started.md](docs/getting-started.md))

| ส่วน | เทคโนโลยี | หมายเหตุ |
| :--- | :--- | :--- |
| **Frontend** | **Next.js (TSX) + Tailwind CSS** | หน้าเว็บแยกตาม Role ในแอปเดียว (`apps/web`) ใช้ UI Kit กลางและแนวทางหน้าตาตาม [DESIGN-apple.md](DESIGN-apple.md) |
| **Backend** | **NestJS (TypeScript)** | REST API + OpenAPI, Validation ด้วย `class-validator`, รูปแบบ Error เดียวกันทุก Service |
| **Message Broker** | **RabbitMQ** | รันใน Docker Compose บนเครื่อง ใช้ส่ง Event ระหว่าง Service |
| **Database** | **PostgreSQL** | รันใน Docker Compose บนเครื่อง — 1 instance แต่แยกฐานข้อมูลต่อ Service (`identity_db`, `job_db`, …) ตาม `docker/postgres/init.sql` |
| **ORM** | **Prisma** | `schema.prisma` ต่อ 1 Service; ตั้งทั้ง `<PREFIX>_DATABASE_URL` และ `<PREFIX>_DIRECT_URL` เป็นค่าเดียวกัน |
| **File Storage** | **RustFS** | ที่เก็บไฟล์แบบ S3 รันใน Docker Compose บนเครื่อง ใช้ผ่าน S3 API (`@aws-sdk/client-s3`) เก็บเรซูเม่ รูปโปรไฟล์ โลโก้ เอกสารบริษัท และ PDF ใบรับรอง |
| **Email** | **Mailpit** | SMTP จำลองใน Docker Compose อีเมลทั้งหมดของระบบดูได้ที่ http://localhost:8025 (ไม่ส่งออกไปยังอีเมลจริง) |
| **Repository** | **Monorepo (pnpm workspaces)** | `apps/` = `web`, `gateway`, และ 5 Services; `libs/` = `contracts` (ชนิดข้อมูล Event/DTO) และ `common` (Guard, Logger, Correlation ID); เอกสารอยู่ใน `docs/` |
| **Container / CI** | **Docker Compose / GitHub Actions** | CI รัน Lint, Test, Build; ทำงานผ่าน Branch + Pull Request |

## 5. แนวทางการพัฒนาตาม SDLC (System Development Life Cycle)
1. **Planning & Requirement Analysis:** วิเคราะห์ปัญหาการประสานงานฝึกงาน กำหนดกฎ Tag ทักษะและสิทธิ์สมาชิก HR ตามสายงาน, ลำดับการอนุมัติระหว่าง HR–นักศึกษา–อาจารย์, ค่า SLA และเกณฑ์ต่าง ๆ ใน config กลาง และวางแผน UAT Test Cases
2. **System & Architecture Design:** ออกแบบสถาปัตยกรรม Microservices (5 Services + API Gateway) ใน Monorepo, Prisma Schema ของแต่ละ Service, API Contract (OpenAPI), Application State Machine และ Event Catalog (Envelope มี `event_id`, `version`, `correlation_id`) โดยเอกสารทั้งหมดเก็บในโฟลเดอร์ `docs/` ของ Monorepo และอัปเดตผ่าน Pull Request
3. **Implementation:** พัฒนาแยกตามราย Service โดยยึดหลัก **1 คน = เจ้าของ Service หลักของตน** ตามตารางหัวข้อ 9 (Notification Service เป็นของ Junior Developer) ทุก Service ใช้ NestJS + Prisma ตามเทมเพลตเดียวกัน (โครงโฟลเดอร์ รูปแบบ Error การตรวจ JWT การเขียน Outbox) และแชร์โค้ดผ่าน `libs/contracts` กับ `libs/common` เท่านั้น
4. **Testing & Integration:**
   - **Automated Test:** แต่ละ Service เขียน Unit / Integration Test ด้วย **Mocha + Chai + Sinon** และวัด Coverage ด้วย **c8** ทดสอบ API ด้วย `supertest` กับ Test Database แยก (Docker) ไม่ใช้ฐานข้อมูลจริง เคสสำคัญที่ต้องมีเทสอัตโนมัติ ได้แก่ State Machine ใบสมัคร, การจอง/คืนโควตาแบบ Atomic (รวมกรณียิงพร้อมกัน), Idempotency ของ Consumer และสิทธิ์สมาชิก HR ตามสายงาน
   - **CI:** GitHub Actions รัน Lint, Test และ Build ของ Service ที่ถูกแก้ทุก Pull Request (รันเทสบน CI แทนเครื่องของแต่ละคนเพื่อไม่ให้เครื่องหนักเกินไป)
   - **Integration & UAT:** ทดสอบการส่ง Event ข้าม Service และ UAT ตามหัวข้อ 8 โดย **ผู้ทดสอบต้องไม่ใช่เจ้าของ Service ที่ทดสอบ** (Lifecycle Service ซึ่ง Tester เป็นเจ้าของ ให้ PM และ Junior Developer เป็นผู้ทดสอบหลัก)
5. **Deployment & Demo:** รัน PostgreSQL, RabbitMQ, RustFS และ Mailpit ด้วย **Docker Compose** บนเครื่อง ส่วนแต่ละ Service และหน้าเว็บรันด้วย **pnpm** เพื่อให้แต่ละคนเปิดเฉพาะส่วนที่กำลังทำ และสาธิตบนเครื่องของทีมโดยไม่ Deploy ขึ้น Cloud (ดู [docs/getting-started.md](docs/getting-started.md))

| **4. ผู้ดูแลแพลตฟอร์ม** <br>*"คุณนนท์ (Platform Admin)"* | ทีมงานผู้ดูแลระบบหลังบ้านของแพลตฟอร์มที่คอยคัดกรองบริษัทและประกาศงาน | อนุมัติบัญชีบริษัทที่เชื่อถือได้ และจัดการเคสที่ถูกรายงานโดยใช้เวลาตรวจน้อยที่สุด และรู้ทันทีว่าคิวใดเกินกำหนด | หากไม่มีคิวและธงบริษัทช่วยจัดลำดับ ทีมงานหลังบ้านจะต้องเสียเวลาไล่ตรวจทุกเคสตั้งแต่ศูนย์ และเสี่ยงถูกใช้ระบบรายงานกลั่นแกล้งบริษัท |

## 7. แผนการดำเนินงาน 4 สัปดาห์ (Work Plan)

| สัปดาห์ | เป้าหมาย | สิ่งที่ทำ | ผลที่เห็นได้ |
| :---: | :--- | :--- | :--- |
| **1** | วางแผนและเตรียมระบบ | สรุปความต้องการ ออกแบบระบบและหน้าจอ เตรียมเครื่องมือของทีม และทำระบบสมัครสมาชิก/เข้าสู่ระบบ | อาจารย์เพิ่มนักศึกษาเข้าระบบได้ และผู้ดูแลอนุมัติบัญชีบริษัทได้ |
| **2** | ประกาศงานและความน่าเชื่อถือ | บริษัทสร้างประกาศงานพร้อม Tag ทักษะ ระบบรายงานประกาศที่น่าสงสัย และคิวตรวจของผู้ดูแล | บริษัทโพสต์งานแล้วขึ้นหน้าค้นหาทันที และประกาศที่ถูกรายงานครบเกณฑ์ถูกระงับอัตโนมัติ |
| **3** | สมัครงานและอนุมัติฝึกงาน | นักศึกษาค้นหาและสมัครงาน บริษัทส่งข้อเสนอ นักศึกษายืนยัน อาจารย์อนุมัติ และระบบเตือนเมื่อมีขั้นตอนค้าง | เห็นใบสมัครเดินครบตั้งแต่สมัครจนเริ่มฝึกงาน |
| **4** | ประเมินผล ใบรับรอง และทดสอบ | บริษัทประเมินผลและออกใบรับรองดิจิทัล นักศึกษารีวิวบริษัท อาจารย์บันทึกผลวิชา และทีมทดสอบทั้งระบบ | ระบบครบทุกขั้นตอน พร้อมผลการทดสอบและสไลด์นำเสนอ |

## 8. การทดสอบการยอมรับของผู้ใช้งาน (User Acceptance Testing - UAT)

| รหัสทดสอบ | ชื่อกรณีศึกษา (Test Case) | ผู้ทดสอบ (Actor) | ขั้นตอนการทดสอบ (Test Steps) | ผลลัพธ์ที่คาดหวัง (Expected Result) |
| :---: | :--- | :--- | :--- | :--- |
| **UAT-01** | การบล็อกการโพสต์งานของบริษัทที่ยังไม่ผ่านการอนุมัติ | HR | 1. สมัครบัญชีบริษัทใหม่ (Admin ยังไม่กด Approve) 2. กด "เผยแพร่งาน" | ระบบไม่อนุญาตให้เผยแพร่และแจ้งเตือนว่ารอการอนุมัติบัญชีจาก Admin |
| **UAT-02** | Tag ทักษะของประกาศงาน | HR & Admin | 1. Admin เพิ่ม Tag `NextJs` และ `Rust` ในรายการกลาง 2. HR สร้างงานโดยเลือก Tag จากรายการ 3. HR พยายามส่งงานที่ไม่มี Tag, มี Tag เกิน 10 รายการ หรือใช้ Tag ที่ไม่อยู่ในรายการ 4. Admin ปิดใช้งาน Tag หนึ่ง | ข้อ 2 งานติด Tag และ `PUBLISHED` ทันที; ข้อ 3 ถูกปฏิเสธ `400 VALIDATION_FAILED`; ข้อ 4 Tag ไม่ขึ้นให้เลือกใหม่ แต่ประกาศเดิมยังแสดง Tag นั้น |
| **UAT-03** | แก้ไขประกาศที่เผยแพร่แล้ว | HR | 1. เปิดงานที่ `PUBLISHED` 2. แก้ไข `description` และเพิ่ม/ลด Tag 3. บันทึกการแก้ไข 4. ตรวจหน้าค้นหา | งานยังคง `PUBLISHED` ไม่ถูกซ่อน ไม่มีการตรวจซ้ำ (ยกเว้นบริษัทที่ติดธง `UNDER_REVIEW` ซึ่งต้องผ่าน Admin อีกครั้ง) |
| **UAT-04** | การเผยแพร่ประกาศทันที | HR (Approved) | 1. ใช้อีเมลองค์กรที่ผ่านการอนุมัติแล้ว (บริษัท `VERIFIED`) 2. สร้างงานที่กรอกข้อมูลบังคับครบและเลือก Tag 3. ส่งประกาศ | งานเปลี่ยนเป็น `PUBLISHED` ทันทีและขึ้นหน้าค้นหา (กรองด้วย `?tags=` ได้) |
| **UAT-05** | การระงับงานอัตโนมัติเมื่อถูกรายงาน (Community Report) | นักศึกษา 3 บัญชี และ Admin | 1. นักศึกษา 3 บัญชีรายงานประกาศงานเดียวกัน<br>2. Admin ตรวจสอบคำร้อง (ยกคำร้อง หรือ ยืนยันระงับถาวร) | งานถูกระงับชั่วคราว (`SUSPENDED`) ทันทีเมื่อครบ 3 บัญชี และเข้าคิวให้ Admin ตัดสินชี้ขาด; ยกคำร้อง → `PUBLISHED` ทันทีและตัวนับรีเซ็ต; ยืนยันระงับ → `REMOVED` |
| **UAT-06** | ลำดับการอนุมัติฝึกงานระหว่าง HR นักศึกษา และอาจารย์ | นักศึกษา, HR & อาจารย์ | 1. นักศึกษากดสมัครงาน 2. HR กดรับพร้อมระบุ `start_date`/`end_date` (`HR_ACCEPTED`) 3. นักศึกษายืนยันรับข้อเสนอ (`ADVISOR_PENDING`) 4. อาจารย์กดอนุมัติ (`ADVISOR_APPROVED`) 5. HR กดยืนยันเริ่มงาน<br>*(ทดสอบซ้ำกรณีอาจารย์กดไม่อนุมัติโดยไม่ใส่เหตุผล และกรณีใส่เหตุผล)* | สถานะเปลี่ยนเป็น `IN_PROGRESS` เมื่อ HR ยืนยันเริ่มงาน; หากอาจารย์ไม่อนุมัติโดยไม่ใส่เหตุผล ระบบไม่อนุญาต; หากใส่เหตุผล สถานะเป็น `ADVISOR_REJECTED` คืนโควตาให้บริษัท และแจ้งนักศึกษากับ HR พร้อมเหตุผล |
| **UAT-07** | การป้องกันปิดปากนักศึกษา (Review Silencing) | HR & นักศึกษา | 1. HR กดประเมินนักศึกษาว่า `FAIL` (พร้อมเหตุผล) 2. นักศึกษาพยายามเขียนรีวิวบริษัท | นักศึกษาเขียนรีวิวได้สำเร็จ แต่มีป้ายกำกับว่ารีวิวนี้มาจากนักศึกษาที่ไม่ผ่านเกณฑ์ |
| **UAT-08** | การป้องกันปั๊มใบเซอร์ (Certificate Farming) | HR | 1. HR ส่งข้อเสนอที่ `end_date − start_date` < 30 วัน<br>2. กรณีฝึกจริง: HR ยืนยันเริ่มงานแล้วพยายามประเมินก่อนถึง `end_date`<br>3. กรณียุติกลางคัน: HR ยุติการฝึกที่วันที่ 10 แล้วพยายามกดออก E-Certificate | ข้อ 1 ระบบปฏิเสธการส่งข้อเสนอ; ข้อ 2 ระบบไม่เปิดให้ประเมิน; ข้อ 3 ระบบปฏิเสธการออกใบเนื่องจากฝึกจริงยังไม่ถึง 30 วัน และอาจารย์ตัดสิน `academic_result` เอง |
| **UAT-09** | การออก E-Certificate และการยืนยันผลรายวิชา | HR, นักศึกษา & อาจารย์ | 1. ฝึกงานครบตาม `end_date` (ฝึกจริง ≥ 30 วัน) 2. HR กด `PASS` และออก E-Certificate 3. นักศึกษาเข้าดาวน์โหลด 4. อาจารย์บันทึก `academic_result` เป็น `ACADEMIC_PASS` | ระบบสร้าง E-Certificate (PDF) ให้นักศึกษาดาวน์โหลดได้ สถานะใบสมัครเป็น `COMPLETED` |
| **UAT-10** | การอนุมัติบัญชีบริษัทและอาจารย์โดย Admin | Admin, HR & อาจารย์ | 1. HR สมัครด้วยอีเมลสาธารณะ (เช่น Gmail)<br>2. HR สมัครด้วยอีเมลองค์กรพร้อมเอกสารไม่ครบ → Admin ตอบ `NEED_MORE_INFO`<br>3. HR ส่งเอกสารครบ → Admin อนุมัติ<br>4. อาจารย์สมัครด้วย `@ac.th` และ Admin อนุมัติ | ข้อ 1 ระบบไม่รับอีเมลสาธารณะ; ข้อ 2 สถานะ `NEED_MORE_INFO` พร้อมแจ้งสิ่งที่ต้องส่งเพิ่ม; ข้อ 3 บัญชีเป็น `VERIFIED` และโพสต์งานได้; ข้อ 4 อาจารย์เข้าใช้งานได้หลังอนุมัติ |
| **UAT-11** | ประกาศของบริษัทที่ติดธงผ่านคิว Admin | HR & Admin | 1. บริษัทถูกติดธง `UNDER_REVIEW` 2. HR ส่งงานสองงาน 3. Admin อนุมัติงานหนึ่ง และปฏิเสธอีกงานหนึ่ง | งานเข้า `PENDING_REVIEW`; ที่อนุมัติเป็น `PUBLISHED`; ที่ปฏิเสธเป็น `ADMIN_REJECTED` พร้อมแจ้ง HR |
| **UAT-12** | สิทธิ์สมาชิก HR ตามสายงาน | HR Owner & HR Member | 1. Owner เชิญสมาชิกและกำหนดสาย `Tech & IT` 2. สมาชิกสร้างงานสาย `Tech & IT` 3. สมาชิกพยายามสร้าง/แก้งานและดูผู้สมัครของสาย `Business & Marketing` 4. Owner เพิ่มสาย `Business & Marketing` ให้สมาชิก แล้วสมาชิกรีเฟรช Token | ข้อ 2 ทำได้; ข้อ 3 ถูกปฏิเสธ `403 FORBIDDEN_ROLE` (`details[].issue` = `FORBIDDEN_CATEGORY`) และรายการประกาศ/ผู้สมัครไม่แสดงของสายอื่น; ข้อ 4 หลังรีเฟรชทำได้ Owner เห็นทุกสายตลอด |
| **UAT-13** | อาจารย์เพิ่มนักศึกษาด้วยฟอร์ม | อาจารย์ & นักศึกษา | 1. อาจารย์ที่ `ACTIVE` กรอกฟอร์มเพิ่มนักศึกษา (อีเมล `@ac.th`, ชื่อ, รหัสนักศึกษา, สาขา, ชั้นปี) 2. นักศึกษาเปิดลิงก์คำเชิญตั้งรหัสผ่านและยอมรับนโยบาย 3. อาจารย์กรอกอีเมลซ้ำ 4. อาจารย์ส่งคำเชิญซ้ำ/ยกเลิกคำเชิญที่ยังไม่ถูกใช้ | ข้อ 1 ส่งอีเมลคำเชิญ; ข้อ 2 บัญชี `ACTIVE` และผูกกับอาจารย์เป็น `LINKED` ทันที สมัครงานได้; ข้อ 3 `409 STATE_CONFLICT` (`EMAIL_ALREADY_REGISTERED`); ข้อ 4 ลิงก์เดิมใช้ไม่ได้เมื่อส่งใหม่/ยกเลิก |
| **UAT-14** | กติกาแก้ไขฟิลด์โครงสร้างกับฟิลด์ข้อความ | HR | 1. เปิดงาน `PUBLISHED` แล้วแก้ `quota` และวันปิดรับ 2. แก้ `description` เพียงเล็กน้อย | ข้อ 1 และข้อ 2 ไม่ตรวจซ้ำ งานยัง `PUBLISHED` (ยกเว้นบริษัทที่ติดธง `UNDER_REVIEW`: ข้อ 2 งานถูกซ่อนและตรวจซ้ำ `VERIFYING` — ข้อ 1 ยังไม่ตรวจซ้ำ); ถ้าพยายามเปลี่ยน `category` ได้ `400 CATEGORY_LOCKED` |
| **UAT-15** | ย้ายอาจารย์ที่ปรึกษาและตัวกรองรายชื่อนักศึกษา | อาจารย์ & Admin | 1. อาจารย์มีนักศึกษาหลายชั้นปี บางคนกำลังฝึกงาน (`IN_PROGRESS`) บางคนฝึกงานเสร็จแล้ว (`COMPLETED`) 2. อาจารย์กรองรายชื่อตามชั้นปี, กำลังฝึกงาน, ฝึกงานเสร็จแล้ว 3. Admin ย้ายนักศึกษาที่มีใบสมัครค้างอยู่ไปอาจารย์อีกคน | ข้อ 2 รายชื่อตรงตามตัวกรอง; ข้อ 3 ย้ายอาจารย์ได้และใบสมัครที่ค้างย้ายตามนักศึกษา; อาจารย์เดิมไม่เห็นนักศึกษาคนนั้นอีก |
| **UAT-16** | สมัครหลายที่และยืนยันได้ทีละ 1 ที่ | นักศึกษา, HR 2 บริษัท & อาจารย์ | 1. นักศึกษาสมัคร 3 บริษัท 2. 2 บริษัทตอบรับ 3. นักศึกษายืนยันบริษัท A 4. บริษัท B (ที่ตอบรับไว้) และบริษัท C (ที่ยัง `PENDING`) ถูกตรวจสถานะ 5. อาจารย์อนุมัติ 6. บริษัท C พยายามกดตอบรับระหว่างขั้นตอน | ข้อเสนอของ B เป็น `STUDENT_DECLINED` และคืนโควตา; ใบสมัคร C เป็น `WITHDRAWN` เมื่ออาจารย์อนุมัติ; ปุ่มตอบรับของ C ถูกปิดระหว่างที่นักศึกษามีใบสมัครที่ยืนยันแล้ว |
| **UAT-17** | โควตาตำแหน่งและการแข่งขันพร้อมกัน | HR & นักศึกษา | 1. ประกาศมี `quota` = 1 และมีผู้สมัคร 2 คน 2. HR กดตอบรับทั้งสองคนพร้อมกัน (ยิงคำขอพร้อมกันจากสคริปต์) 3. คนที่ได้ข้อเสนอปฏิเสธหรือหมดเวลา | ตอบรับได้เพียง 1 คน อีกคนถูกปฏิเสธเพราะโควตาเต็ม (ไม่เกินโควตาแม้ยิงพร้อมกัน); เมื่อข้อเสนอถูกปฏิเสธ/หมดเวลา โควตาถูกคืนและกดตอบรับอีกคนได้ |
| **UAT-18** | การหมดเวลาและการเตือนตาม SLA | ระบบ, HR, นักศึกษา & อาจารย์ | *(ปรับ config ให้เวลาเร็วขึ้นสำหรับทดสอบ)* 1. HR ไม่ตอบใบสมัคร 2. นักศึกษาไม่ยืนยันข้อเสนอ 3. อาจารย์ไม่อนุมัติ | ส่งการแจ้งเตือนตามกำหนด; ข้อ 1 เป็น `EXPIRED`; ข้อ 2 เป็น `EXPIRED` และคืนโควตา; ข้อ 3 แจ้ง Admin และไม่อนุมัติอัตโนมัติ |
| **UAT-19** | คิว Admin เกิน SLA | Admin & HR | 1. มีเคสเข้าคิวปกติและคิว Fast-Track (เช่น ประกาศของบริษัทที่ติดธง, คำร้อง Report) 2. ปล่อยเกินเวลา SLA ของแต่ละคิว | รายการที่เกินกำหนดแสดงป้าย `OVERDUE` สีแดง; Fast-Track อยู่ลำดับต้นของคิว |
